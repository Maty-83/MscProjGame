	Controls to be implemented:
	
		>Mouse controls:
			>Two ways you can do mouse controls.
				>Direct: 
					>Mouse controls acceleration (Mouse moving = accelerate in that direction)
					>Great if you don't damp the acceleration (Precise frame-by-frame control)
					>By modifying the mouse delta sensitivity, we can achieve extremely precise control in a given axis.
					>Would be good to have a "Control overflow" feature, so exact frame and control timing doesn't influence acceleration, only total displacement does.
						>Counter on mouse.
				>Indirect:
					>Mouse displacement controls maximum (rotational) velocity
					>If you intend to damp inputs, having this continuous input is a better idea.
					>Implementation is also fairly straightforward. We accelerate towards the desired total vector.
					>Disadvantage: No way to "clear" input precisely becomes a significantly greater issue than a direct control.
						>Needs a way to clear these (Already partially implemented): Middle mouse is perfect for this.
						>Or we can have non-linear curves/deadzone, similar to what is used by controllers to counteract stick drift!
			>We borrow a term for this from E:D: "Relative mouse"
					
					
		>Throttle control:
			>If we're damping inputs, keeping a continuous throttle allows us having a player constantly keep the thrust button pressed.
			>Inherited from airplanes as they are.
			>Many implementations across different genres (As just one example, WT uses it for planes), so would be good to test for our purposes.
			>Precise control again becomes an issue.
				>"Throttle cut" key? E:D uses 'X' for it.
				>Or "Stop and re-press" when reaching zero?
				
			>Testing if throttle control on multiple axes helps would be interesting.
		
		>Which axes to damp?
			>Primary aim of the study is to figure out comfortable controls.
			>We're looking for a control scheme the players like and which preserves good performance.
			>Damping a part of the comfort of the control scheme (Familiar to those who've played flight sims, easier orientation in space by partly coupling ship forward vector and direction of travel)
			>Also a part of actually HANDLING the controls (Automatic recovery from rotation the player lost control over.)
			>Some axis coupling possible (Pitch & Yaw, Lateral & Vertical)
			
		>Actually programming in the mouse inputs:
			>Delta is not limited to +1/-1 range.
			>But that's a good thing, since it records the movement.

				>We detect which if any axis is using it and store it that way. Then, using that detected use we can calculate the input.

		>Notes on fixes to velocity, etc.
			>I aggressively clamp maximum velocity every frame instead of nicely slow it down.
				>Prevents exceeding the velocity with any means, setting a speed limit for the player
				>Since this is done on the whole vector, means accelerating in multiple axes won't allow for faster ships.
					>Question here on gameplay: Should acceleration be allowed to be faster in that manner?
						>Gameplay-wise it's a weird skill-based dilemma between what I want
					
		>Design of publically selectable variables for control inputs
			>Maximum acceleration and velocity in a given axis
				>For tuning the handling model and POTENTIALLY changing this with effects in-game (Long ways off, probably not in thesis. But I wanna continue work on the game after anyway.)
			>Input sensitivity:
				>Multiplier on axis input.
			>Input types:Three main types+Damping
				>Damping: Should we automatically decellerate to 0 w/o other input?
				>Three main types of inputs:
					>Direct: Inputs are given per-frame, on interval [-1,1]
						>Essentially clamped accumulator, so defaults to it.
						>Intended to be used primarily with keyboard controls, as it works perfectly with digital keyboards.
							>Also useful for analog ones by extent, with greater precision allowed.
					>Accumulator: Accumulates for how many physics frames the input should be executed based on length of held input. (Every frame we add sensitivity*axis input to the total, which is clamped to some reasonable value)
						>Useful especially for mouse movement, where to precisely end up at a given speed, we now only measure total distance, not time spent moving the mouse.
							>Much easier for most humans.
						>Naturally decays
					>Throttle:
						>How much input accumulates determines the speed we try to match.
						>So if we say our throttle is 0.3 of the max accumulation, the throttle doesn't decay. Our ship tries to match its velocity in the given axis to 0.3*maximum velocity in that axis.
						>Very useful as a default damped movement for the mouse, as we specify velocity by mouse offset
						>Also useful in "throttle" analogy for atmospheric aircraft, simulates HOTAS throttle.
						>One note: If accumulation to full throttle is set very low compared to max accumulation, simulates mouse-offset direct controls via mouse too.
				>Use enum which specifies type+Damping
				>Throttle already damps, doesn't need it

	>Level functionality: Checkpoints
		>Checkpoints make it so we can design a more complex race course that overlaps, rather than the course just being the fastest route from A to B
			>That also introduces a popular passtime of many players, shortcuts!
			>We may want to force a certain order of checkpoints
		>Since the design is evolving, I'd rather over-build the system and not use certain functions than later regret not having it.
		>It means if you create levels, all you need to do is set them down and potentially set up priorities, with the code handling everything else.
		>Idea: Use a SortedList<TKey,TValue> with TKey being the checkpoint priority (lower is better) and TValue being a list of checkpoints.
			>That also solves our issue of guiding the player to the next checkpoint, if that pops up as a necessity.
			>Checkpoints can be set to be permissive or not, either via a general setting, or individually (E.G. we can have multiple same-priority checkpoints unlocking a route, but another set unlocking only after going through that route.
			>Maintaining a reference this way also allows checkpoints themselves to "Decide" if they can be taken, with a public priority "Telling" them the current priority.
			>Could even have proactive "Linked checkpoint" code to allow multi-routing.
				>Exclusive with same-priority unlocks to do easily, but eh.
			>Basic blueprint is as such:
				>On checkpoint Start() method, call the singleton and add yourself to its checkpoint SortedList
				>OnCollisionEntered with the inside and ship, call singleton with your index and reference, telling it to remove you from the list of outstanding checkpoints.
					>If this removes the final element from the SortedList, remove entry entirely from SortedList.
					>If SortedList is empty, we can finish.
				>NOTE: Keep the total list (Or at least count) somewhere so the player can see the # of checkpoints.
			>Unless specified, we should always have checkpoints of the same priority
				
			>BIG NOTE: We probably want a unique indexing style with two indices for when to unlock checkpoints and to check which checkpoint number this is (Same number checkpoints are linked)
			
			>We also need the ability to remove items from the SortedList easily, as it will be useful for our level editor.
			
			>All checkpoints with the same priority will complete at once (Our linked level)
			
			>We don't permit checkpoint re-use, as that would throw a wrench into our goals
				>It's entirely possible, but the setup is not something worth doing right now.
				
			>We also don't require this to be set.
				>We can exploit a simple idea: Using uint16 for the indices in the checkpoints, and then negative indices for the ones unspecified!
					>Those will follow placement priority likely (Depends on how instantiating GameObjects adds new ones, since Update() goes through the list linearly
						>May break if multithreading.
